# Groups

**Your people, every day.** A tiny app for one friendgroup, built as an iPhone
home-screen app.

- **Hangout** — one tap nudges everyone in your group. Whoever says *yes* gets
  your location, and you get told they're in.
- **Daily Memories** — film up to 3 minutes, drop it in the vault. At **20:00**
  every day the vault opens and the group's clips play back as one film, oldest
  first. Save the whole day to your camera roll.

It installs through Safari's **Add to Home Screen**: full screen, its own icon,
its own splash screen, offline shell, and real lock-screen notifications.

The look and the reasoning behind it are in [DESIGN.md](DESIGN.md).

---

## What's in the box

```
server/     zero-dependency Node backend (HTTP, SQLite, Web Push, video)
web/        the PWA — vanilla ES modules, no build step
scripts/    icon generator, VAPID keys, the test suites
deploy/     Caddy config, and the Oracle Cloud walkthrough
.github/    the workflow that publishes the app to GitHub Pages
```

**No npm dependencies.** Not "few" — none. `node_modules` is empty on a fresh
clone. SQLite comes from `node:sqlite`, Web Push (VAPID + RFC 8291 payload
encryption) is implemented on `node:crypto`, and the icons and iOS splash
screens are generated by a PNG encoder written on `node:zlib`. The only optional
external is `ffmpeg`, for stitching a day into one downloadable MP4.

Requires **Node 22.5+** (for `node:sqlite`).

## Run it

```bash
git clone <this repo> && cd groups
npm run icons          # generate the app icon + iOS splash screens
npm start              # http://localhost:8080
```

That's the whole setup. The database, the videos and a generated VAPID key pair
land in `./data/`.

```bash
npm run dev            # same, with --watch
npm test               # 79 API + PWA checks, no browser needed
node scripts/reel-test.mjs      # exercises the ffmpeg stitcher (skips if absent)
node scripts/visual-check.mjs   # drives the real UI in Chromium, needs Playwright
node scripts/pages-check.mjs    # the app on one origin, the API on another
```

## Hosting it

Groups is two halves, and they can live in different places:

| | | |
| --- | --- | --- |
| **the app** | HTML, CSS, JS, icons | any static host — **GitHub Pages works** |
| **the server** | groups, clips, hangouts, push | needs Node + a disk |

Whichever you choose, it has to be **HTTPS**. That is not a nicety — Safari gates
the camera, geolocation, service workers and push notifications behind a secure
context, so over plain HTTP on a LAN address you get an app that cannot film,
cannot locate you and cannot notify you.

### GitHub Pages — the app, installable, free, forever

`.github/workflows/pages.yml` publishes `web/` to Pages on every push. You get a
permanent HTTPS link like `https://<you>.github.io/groups/` that anyone in the
group can open in Safari and **Add to Home Screen**. Nothing to run, nothing to
pay for, and the link never changes even if you move servers later.

1. **Settings → Pages → Source: GitHub Actions.** One click, once. (Actions is
   not allowed to switch Pages on for a repo by itself, so this is the one bit
   that cannot be automated — the workflow tells you so if you forget.)
2. Push, or run **Publish app to Pages** from the Actions tab.
3. The run summary prints the URL.
4. Open it on your iPhone → Share → **Add to Home Screen**.

Pages serves static files only, so **it cannot run the server half**. The first
time anyone opens the link the app asks for their group's server address, then
remembers it. Set a `GROUPS_API_BASE` repository variable (Settings → Secrets
and variables → Actions → Variables) and the workflow bakes it in, so nobody is
ever asked:

```
GROUPS_API_BASE = https://groups.yourdomain.com
```

Invite links carry the server too — `…/groups/?s=https://your-server&join=A1B2C3`
— so a friend taps one link, signs up, and is in the group without typing an
address at all. Settings → Invite friends generates it.

Everything works across the two origins: the app authenticates with a bearer
token, videos play from short-lived signed URLs, and the live event stream uses
a one-off ticket. The session cookie is deliberately never sent across origins,
which is why the server can safely accept requests from your Pages domain.

> If you would rather one thing served one thing: run the server, and it serves
> the app itself at `/`. Pages is optional.

### Fly.io — one machine, one volume, done

Cheapest path to a real domain with automatic TLS.

```bash
fly launch --no-deploy                       # accept the bundled fly.toml
fly volumes create groups_data --size 10     # SQLite + the videos live here
fly secrets set $(npm run --silent keys | grep VAPID | xargs)
fly deploy
```

`fly.toml` is set up with a persistent volume at `/data`, a health check on
`/api/health`, and `auto_stop_machines = "suspend"` so an idle friendgroup costs
close to nothing while still waking instantly.

### Oracle Cloud Always Free — free, with real disk, never sleeps

The pick if you want it in the cloud and genuinely free: an Arm machine with
200 GB that does not expire and does not idle out. Step by step, including the
two firewalls that catch everyone: **[deploy/ORACLE.md](deploy/ORACLE.md)**.

### Docker on any VPS — with TLS included

```bash
cp .env.example .env          # set GROUPS_DOMAIN, then npm run keys for VAPID
docker compose up -d
```

Point the domain's A record at the box first. Caddy fetches and renews the
certificate itself, proxies to the app, and is configured for the two things
that trip up a default reverse proxy here: a 256 MB body limit (a 3-minute
1080p clip) and unbuffered responses (the live event stream).

### Railway / Render / any Docker host

Point it at the `Dockerfile`, attach a persistent volume at `/data`, and set the
`VAPID_*` variables. That's all the configuration there is.

### Locking the server down to your Pages site

By default the server answers any web origin. That is safe — cross-origin
requests never carry the session cookie, so a hostile page gains nothing — but
if you would rather be explicit:

```
ALLOWED_ORIGINS=https://you.github.io
```

### Just a Node process

```bash
DATA_DIR=/var/lib/groups PORT=8080 node server/server.mjs
```

…behind nginx or Caddy for TLS. Give the proxy a long timeout for uploads and
turn buffering off for `/api/stream`.

### Testing on your actual phone before you deploy

```bash
npm start
cloudflared tunnel --url http://localhost:8080   # or: ngrok http 8080
```

Open the HTTPS URL it prints on the iPhone. Everything works there, Add to Home
Screen included.

## Configuration

Every setting is optional.

| Variable | Default | What it does |
| --- | --- | --- |
| `PORT` | `8080` | Port to listen on |
| `HOST` | `0.0.0.0` | Interface to bind |
| `DATA_DIR` | `./data` | SQLite database, videos, generated VAPID keys |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | generated | Web Push identity — `npm run keys` |
| `VAPID_SUBJECT` | `mailto:hello@groups.app` | Contact address sent to push services |
| `ALLOWED_ORIGINS` | any | Comma-separated web origins allowed to call the API |
| `INSECURE_COOKIES` | unset | Set to `1` for plain-HTTP local dev |
| `LOG_REQUESTS` | unset | Set to `1` for a request log |

If you leave the VAPID variables unset the server generates a pair on first boot
and keeps it in `DATA_DIR/vapid.json`, so notifications survive restarts without
any setup. Set them explicitly if you ever want to move hosts and keep existing
push subscriptions alive.

### How much disk?

A 3-minute 1080p iPhone clip is roughly 200 MB; most are far shorter. A group of
five posting a couple of clips a day sits comfortably in 10 GB for a few months.
Clips are stored as uploaded — nothing is re-encoded unless someone asks to save
a whole day in one file.

## Using it

1. Open the site, pick a name and an emoji. You get a **six-word recovery
   phrase** — that *is* your account. No email, no password, no phone number.
2. Create a group. Share the six-character code or the invite link.
3. **Add to Home Screen** from the Safari share sheet.
4. Open it from the home screen and turn on notifications in Settings. iOS only
   allows push from an installed app, which is why the order matters.

### The 20:00 rule

A memory day runs **from one 20:00 to the next**. Film something at 21:00 and it
goes into *tomorrow's* memory — so nothing ever appears in a reel you already
watched, and every drop is a full 24 hours of the group's life. Before the drop
you can see how many clips are waiting and who filmed them, never what's in them.

The hour is per group (Settings → Memories open at) and so is the time zone, so
a group spread across countries still opens together.

### Privacy of the location trade

A hangout ping carries the host's location, but the server only ever sends it to
people who answered **yes** — and to the host, it sends back the location of
whoever is in. Say no, or say nothing, and you never see it. Change your mind to
no and it disappears again. That rule lives in one function on the server
(`hangoutView` in `server/api.mjs`) and is covered by the tests.

## How it works

| | |
| --- | --- |
| **Auth** | A random token per device, stored hashed. Also set as an httpOnly cookie so `<video>` and downloads authenticate without JavaScript. Recovery is a six-word phrase, stored as a hash. |
| **Live updates** | Server-Sent Events per user, with an event log so a phone that slept catches up on reconnect. |
| **Push** | VAPID (RFC 8292) and aes128gcm payload encryption (RFC 8188/8291) written directly on `node:crypto`. Verified against the RFC 8291 test vector in the suite. Notification actions let you answer a hangout from the lock screen. |
| **Recording** | `MediaRecorder` with a feature-detected MIME type — MP4 on iOS, WebM elsewhere. A poster frame is drawn from the video on-device and uploaded alongside. |
| **Uploads** | Streamed straight to disk, never buffered in memory. Queued in IndexedDB first, so a clip filmed with no signal uploads later instead of being lost. |
| **Playback** | Byte-range requests, because Safari will not play a video without them. The next clip preloads while the current one plays. |
| **Stitching** | If clips share a codec and size (a group of iPhones) they're stream-copied — instant and lossless. Otherwise each is normalised to 1080×1920/30fps/AAC first. The result is length-checked, because `ffmpeg -c copy` will exit 0 having quietly dropped a mismatched clip. |
| **Saving to Photos** | The Web Share API with a file, which puts "Save Video" in the iOS share sheet. Falls back to a download elsewhere. |
| **Split hosting** | Nothing is bound to an origin or a path: the app resolves its server at boot (invite link → remembered → bundled `server.json` → this origin), media arrives as signed URLs, and the event stream uses a ticket. That is what lets GitHub Pages host the front end. |

## API

Everything is under `/api`, JSON in and out, `Authorization: Bearer <token>` or
the session cookie.

```
POST   /api/auth/register              {name, emoji}     -> token + recovery phrase
POST   /api/auth/restore               {recoveryPhrase}
GET    /api/me
POST   /api/groups                     {name, emoji, tz}
POST   /api/groups/join                {code}
GET    /api/groups/:id                 members, live hangouts, the vault
POST   /api/groups/:id/hangouts        {vibe, note, lat, lng, hours}
POST   /api/hangouts/:id/respond       {answer, lat, lng}
POST   /api/groups/:id/clips           raw video body + X-Shot-At, X-Duration…
GET    /api/groups/:id/memories        the archive
GET    /api/groups/:id/memories/:day   one memory (locked until it opens)
POST   /api/groups/:id/memories/:day/reel      build the stitched MP4
GET    /api/clips/:id/video            range-enabled stream
POST   /api/stream/ticket              short-lived ticket for EventSource
GET    /api/stream                     Server-Sent Events
GET    /api/health
```
